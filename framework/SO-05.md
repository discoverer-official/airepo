AIRepo — SO-05 Adoption Profiles  
Status: PUBLIC CANONICAL / AIRepo 1.0.0

1\. Mission  
Own the reusable model for declaring how a target project applies AIRepo without making AIRepo itself project authority.

2\. Profile principle  
A Project Profile is project-owned configuration/evidence that binds an exact AIRepo Framework Revision to the project's authority chain, scope, applicable concerns, accepted deviations and execution permissions. It is not an AIRepo semantic owner.

3\. Minimum profile fields  
\- Framework Revision or compatible range;  
\- target project/repository identity;  
\- project authority chain and exact revisions where resolvable;  
\- application mode: Assess | Adopt/Design | Implement | Validate;  
\- applicable semantic concerns/extensions;  
\- known Systems of Record and owners relevant to assessment;  
\- accepted deviations/exclusions and their authority;  
\- implementation permission boundary;  
\- evidence/revision snapshot used for the run.

4\. Applicability  
Core Rules apply according to their Rule applicability. Conditional areas such as prompt, dataset, eval, trace, multi-repository, multi-language or generated-artifact concerns activate only when the project exhibits the corresponding consumer/failure mode.

5\. Adoption is not all-or-nothing structure cloning  
A project adopts semantic invariants and explicitly selected applicable requirements; it does not copy a universal directory tree, framework governance process or framework-owned state.

6\. Modes  
Assess — read-only assessment and recommendations; no structural mutation.  
Adopt/Design — prepare project-owned target profile/design and Human Decisions.  
Implement — perform only changes authorized by project authority and the accepted target design.  
Validate — evaluate the declared project revision/profile and produce evidence/verdicts without self-approving project authority.

7\. Deviations  
A project-approved deviation is valid only when the project authority entitled to decide it explicitly accepts the deviation. AIRepo records the result but cannot approve it on the project's behalf.

8\. Small-consumer path  
For a simple repository, the profile may remain minimal. AIRepo must not require empty semantic areas, speculative manifests or conditional extensions merely to resemble a reference profile.

9\. Migration  
Existing v2.0.0 profiles may remain pinned to v2.0.0. Migration to the successor uses SO-08 replacement mappings; semantic-equivalent profile fields should migrate mechanically where possible.
