AIRepo — SO-01 Framework Charter and Scope
Status: PUBLIC CANONICAL / AIRepo 1.1.0

1\. Mission
Provide a reusable, technology-agnostic and provider-neutral framework for organizing engineering assets in repositories and for constraining repository-facing AI-agent behavior so that authority, ownership, provenance, discoverability, lifecycle and compatibility remain explicit.

2\. Problem Statement
Repository evolution, especially under AI-centred engineering, can create duplicate authorities, speculative structures, unclear asset ownership, hidden state, broken navigation and unsafe automated remediation. AIRepo provides a bounded organization model and assessment lens for those repository-facing concerns.

3\. Goals
\- One semantic fact has one authority owner.
\- Repository organization follows semantics, consumers, authority and lifecycle rather than preferred folder patterns.
\- AI agents can assess and propose repository changes without acquiring project authority.
\- Organization decisions remain portable across platforms, providers, languages and tooling.
\- Migration, compatibility, provenance and validation are explicit where applicable.
\- Structural complexity is justified by current consumers and real failure modes.

4\. Non-Goals
AIRepo does not own product workflow, delivery lifecycle, issue tracking, runtime orchestration, product/system architecture, business ownership, staffing, generic approval workflow, model/provider runtime design, evaluation methodology as a domain, dataset science, observability architecture, or universal organization of non-repository knowledge stores.

5\. Scope
AIRepo covers repository-facing semantic classification, ownership, canonical System of Record, placement, naming, discoverability, durability, provenance, structural migration, compatibility, confidentiality boundaries, structural validation, repository-facing AI-agent execution constraints and organization of repository-managed AI engineering assets when those concerns are about organization rather than domain methodology.

6\. Conditional scope
Prompts, datasets, evaluation assets, traces, generated artifacts, packages, multi-repository structures, multi-language implementations and licensed scopes are conditional concerns. They are activated only when an active consumer or reproducible failure mode makes their organization relevant.

7\. Explicit authority boundary
AIRepo is an assessment/design framework and does not become part of a target project's authority hierarchy merely by being applied. The target project's accepted authority chain always wins on project decisions.

8\. Conflict handling
When AIRepo guidance conflicts with project authority, resolve the exact project sources and revisions, identify the winning source, record the conflict and resulting classification, and avoid authority-changing remediation unless permitted by project authority. Human Decision is required only when existing authority cannot resolve the decision.

9\. Human Decision boundary
Human Decision is required for canonical AIRepo semantic change, authority-boundary change, compatibility-breaking change, removal or incompatible reinterpretation of an active Rule, release freeze/promotion, and project adoption actions that alter accepted authority, System of Record, incompatible structure or protected-data controls.

10\. Investigation before decision
Missing evidence does not prohibit read-only investigation, repository analysis, research or targeted validation. It blocks only the authority-bearing claim/action that cannot be safely justified after reasonable evidence acquisition.

11\. Success criteria
AIRepo succeeds when a new consumer can assess, adopt, implement and validate repository organization without inheriting project-specific assumptions, without creating shadow authority, and without requiring framework-owned infrastructure when an existing capability satisfies the required property.
