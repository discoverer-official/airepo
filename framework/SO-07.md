AIRepo — SO-07 AI Agent Execution  
Status: PUBLIC CANONICAL / AIRepo 1.0.0  
Public release identity: AIRepo 1.0.0

1. Mission  
Own reusable AI-agent execution constraints for applying AIRepo while preserving target-project authority and avoiding duplicated prompt semantics.

2. Execution inputs  
An execution consumes: exact Framework Revision; Project Profile; selected mode; applicable Rules; target-project authority/evidence snapshot; tool capabilities and constraints. A Machine Projection MAY be used as a derived execution input but is never required authority.

3. Modes  
Assess — read-only discovery, classification, findings and recommendations.  
Adopt/Design — prepare target profile/design, alternatives and Human Decision material; no unauthorized mutation.  
Implement — execute only changes authorized by project authority and accepted target design; preserve migration/rollback boundaries.  
Validate — collect evidence and evaluate conformance without self-approving project authority or release state.

4. Authority behavior  
The agent must resolve project authority before authority-bearing remediation. It may autonomously investigate missing evidence when read-only/safe. It must not treat prompt text, file location, existing implementation, merge, CI, runtime observation or AI output as approval unless the project's authority model explicitly does so.

5. Evidence acquisition  
Missing evidence first triggers safe acquisition when possible. The agent may search authoritative sources, inspect repository state, run bounded validation and gather exact revisions. If sufficient evidence remains unavailable, it must fail closed on the governed claim/action and record the gap.

6. Bounded execution units  
Apply EXEC-001. Prefer one bounded batch when all changes share the same authority owner, approval boundary, validation boundary and rollback boundary and intermediate partial state would be meaningless or unsafe. Split work when any of those boundaries differ. Batch eligibility is a conjunction, not a convenience override.

7. Generated execution bundles  
Prompt kernels, mode prompts, rule subsets, quick-start instructions, Machine Projections and machine context are generated/adapted views composed from canonical semantic owners plus the Project Profile. They are non-authoritative and revision-bound. Consumers are not required to execute a projection generator.

8. Localization use  
An agent MAY use a Localized Projection for explanation or interaction. Normative identity resolves to the canonical source and stable IDs. A stale or disputed localization cannot override canonical semantics.

9. Evidence closure non-recursion  
Final conformance/adoption evidence binds an immutable subject revision. Evidence produced after that subject, including post-merge validation or closure attestations, references the subject without redefining it. A newer evidence artifact must distinguish its own evidence revision from the subject revision.

10. Human Decision preparation  
Before a required Human Decision, the agent should gather available evidence, identify conflicting/winning sources where resolvable, analyze options/impact, recommend an option and state exactly what remains undecidable. Do not escalate merely because research or repository inspection is still possible autonomously.

11. Safety boundaries  
No unauthorized authority/SoR change; no destructive migration without required approval and rollback; no confidentiality weakening; no maturity/release self-assignment; no hidden project-specific state introduced by AIRepo.

12. Provider neutrality  
Execution semantics do not depend on a specific LLM, agent runtime or vendor. Provider/tool integrations are adapters.
