AIRepo — SO-06 Assessment and Repository Design Method
Status: PUBLIC CANONICAL / AIRepo 1.1.0
Public release parent: AIRepo 1.0.0

1. Mission
Own the reusable method for assessing repository organization, designing bounded improvements and applying the Complexity Budget without imposing a universal topology.

2. Assessment sequence
1) Resolve project authority and exact revision/evidence snapshot.
2) Identify active consumers and material engineering assets.
3) Classify semantic responsibility, owner, SoR, lifecycle, confidentiality and compatibility boundaries.
4) Resolve applicable SO-04 Rules and conditional concerns.
5) State the material Claims being assessed, including the exact subject and claimed property/boundary.
6) Acquire or reuse evidence only after checking Evidence Fitness for each Claim: subject binding, method observability, material-input coverage, freshness/staleness and comparability limitations.
7) Detect failure modes: duplicate authority/state, broken discoverability, speculative structure, misplaced lifecycle, unsupported compatibility, unsafe data handling, unverifiable generated assets, or evidence that cannot actually observe the claimed property.
8) Propose the smallest change that resolves the failure mode.
9) Apply the lightweight complexity screen.
10) Escalate to full scorecard only for material structural/lifecycle impact.
11) Produce target design, migration/rollback where needed, validation requirements, evidence limitations and explicit Human Decisions.

3. Fast Path for routine low-risk work
For Class A/B or low-risk Assess work with no material authority, compatibility, safety, behavior/reproducibility, cross-revision evidence-reuse or Class C/D concern, use the smallest sufficient path:
1) resolve authority only as far as needed;
2) identify the concrete failure;
3) resolve the applicable Rule(s);
4) propose the smallest change;
5) validate the changed property;
6) stop.

Do not require explicit Claim/Evidence-Fitness records on this Fast Path unless a PASS is contested or materially relied upon. Escalate to the full assessment sequence when any excluded concern becomes material.

4. Evidence reuse
Historical evidence MAY be reused when the relevant subject, claim, authority basis and verification assumptions remain materially unchanged. Reuse is claim-relative, not artifact-relative: one changed dependency does not invalidate unrelated evidence, while an exact old PASS cannot support a materially changed subject or an unobserved boundary.

When prior evidence crosses a session, workflow or other execution boundary, AIRepo evaluates only its continuing fitness for the current Claim. Continuation/checkpoint semantics themselves belong to the applicable continuity framework or consumer runtime.

5. Behavior/reproducibility claims
If a Claim depends on effective instructions/context, capability exposure, model/provider/harness, workflow, policy, runtime or evaluator behavior, resolve the material identities from the semantic owners of those inputs. An AICCF Execution Context Manifest, AECF continuation evidence, AAGF governance decision, runtime identity or equivalent consumer artifact may be evidence inputs when applicable. AIRepo does not own or duplicate those external semantics.

6. Lightweight complexity screen
- Which active consumer/failure mode is addressed?
- Can naming/navigation/configuration/composition/existing contract/external capability solve it?
- Does the proposal add an Authority Owner, SoR, canonical location, manifest/config, validator, workflow/registry or compatibility edge?
- Is migration or rollback required?
- What is the less irreversible alternative?

If no material complexity increase is detected, do not require the full scorecard.

7. Full scorecard trigger
Use the full Complexity Budget only when a proposal adds or materially changes structural/lifecycle ownership, multiple canonical locations, Systems of Record, compatibility boundaries, validation mechanisms, migrations, operational support or confidentiality controls.

8. Design rules
- semantic before physical;
- no universal directory topology;
- preserve existing acceptable organization when no material failure exists;
- generated and cached artifacts remain explicitly derived;
- external services are valid canonical locations when project authority/lifecycle requires them;
- conditional AI asset areas are introduced only when present and actively consumed;
- do not add a new evidence registry, behavior manifest or validator when an existing owner/artifact plus claim-relative mapping is sufficient.

9. Output
Assessment outputs should contain evidence-backed findings, applicable Rule IDs, bounded Claims, current-state classification, Evidence Fitness/limitations, failure mode, impact, smallest target change, compatibility/migration impact, validation needs, residual scope and Human Decision only where authority requires it.

10. Implementation boundary
This method may propose changes. Mutation occurs only under an authorized Implement mode and target-project authority. Assessment findings do not self-authorize remediation.
