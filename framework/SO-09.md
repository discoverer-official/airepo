AIRepo — SO-09 Validation and Conformance
Status: PUBLIC CANONICAL / AIRepo 1.1.0
Public release parent: AIRepo 1.0.0

1. Mission
Own reusable applicability, verification, evidence-fitness, validation-result and conformance-verdict semantics for AIRepo while keeping concrete validation evidence outside reusable framework semantics.

2. Minimal conformance model
Normative Rule → applicability → bounded Claim → verification intent → concrete evidence → Evidence Fitness → result → verdict.

3. Applicability
For each Rule: applicable | not applicable | unresolved. Not-applicable requires evidence that the activating condition/consumer is absent. Unresolved applicability cannot be silently treated as satisfied.

4. Validation results
satisfied | approved deviation | non-compliant | insufficient evidence | conflict.

5. Evidence Fitness
Evidence Fitness in AIRepo applies only to Claims used to assess AIRepo applicability, conformance, repository organization, migration or AIRepo execution outcomes. AIRepo does not own generic evaluation methodology and does not define how another Framework establishes its own truth.

Evidence Fitness is evaluated for the specific Claim, not for an artifact in the abstract.

Minimum dimensions when material:
- subject binding — does the evidence refer to the exact subject/revision/boundary claimed?
- method observability — can the verification method actually observe the claimed property or boundary?
- material-input coverage — are inputs whose change could invalidate the Claim represented or otherwise bounded?
- freshness/staleness — has a relevant dependency changed since the evidence was produced?
- comparability/limitations — are mocks, fixtures, alternate providers, synthetic datasets, partial paths or other limitations explicit and compatible with the Claim?

Exact revision binding is necessary where the Claim depends on exact identity, but is not sufficient by itself. A green validator that only checks structure cannot prove runtime behavior; a mock can prove behavior of the mocked contract but not an unexercised external boundary; a transport-compatible test cannot prove full semantic compatibility unless its method covers that semantic surface.

Tests, validators, evals, graders, CI, generated inventories and reports MAY verify a semantic Claim but MUST NOT originate, narrow, replace or promote the semantic authority that the Claim concerns. A validator/authority conflict is a validator/framework defect or unresolved conflict, not automatic consumer non-conformance.

6. Evidence acquisition model
When required evidence is missing, stale, ambiguous or not fit for the Claim, the default next action is read-only investigation/acquisition when safely possible. Fail-closed applies before an authority-bearing outcome when fit evidence remains insufficient.

Prior evidence may be selectively reused when the current Claim, subject and material verification assumptions remain valid. Evidence whose applicability cannot be established is insufficient for that Claim; unrelated valid evidence is not discarded merely because another dependency changed.

7. Self-consistency
A releasable Framework Revision must validate: one semantic owner per fact; no duplicate active Rule IDs; all active Rules resolvable; generated/source consistency; closed replacement references; no competing authority; no project-specific semantic dependency; deterministic assurance classification.

Only when a Machine Projection is actually published for an active machine consumer or distribution profile, additionally validate: exact release/source binding; complete active Rule/SO identity coverage; no unknown owner references; no provider-specific semantic fields; deterministic normalized payload; stale detection on source-hash mismatch.

Only when a Localized Projection is actually published for an active consumer, additionally validate: exact canonical source binding; locale identity; stable identifiers unchanged; stale detection; canonical-source precedence.

8. Independent assurance
Class A: not required by default.
Class B: only when targeted risk warrants it.
Class C: required independent review.
Class D: required independent adversarial review.

9. Consumer validation
Consumer validation is targeted to affected contracts, Claims and failure modes. Class C/D changes require affected-consumer validation; unrelated consumers do not need ceremonial revalidation. Backward-compatible optional projections do not require a consumer to adopt the projection itself to demonstrate compatibility.

For evidence-fitness semantics, validation should include at least one case where exact/revision-bound evidence is correctly accepted for a narrow Claim and at least one case where apparently successful evidence is rejected as insufficient because the method cannot observe the broader Claim.

10. Concrete evidence records
Validation-run evidence is non-authoritative evidence bound to an exact Framework Revision and exact consumer revision. Where evidence is produced after the governed subject, record both subject_revision and evidence_revision; the latter must not redefine the former.

Evidence records should capture only the material fields needed to explain fitness for the Claim. AIRepo does not require a universal evidence database or mandatory all-fields behavior manifest.

11. External behavior/context evidence
When a Claim depends on execution-context composition, capability exposure, continuation, governance, runtime, workflow, policy, model/harness or evaluator identity, AIRepo consumes the relevant revision-bound evidence from the applicable semantic owner. For example, an AICCF Execution Context Manifest may supply context-composition identity while AIRepo decides whether that identity plus other evidence is fit for a conformance Claim. The external artifact remains derived evidence, not AIRepo authority.

12. Generated verification view
A generated Conformance View or Machine Projection may combine Rule IDs, applicability semantics and verification intent for execution convenience. It is a deterministic projection and cannot own Rule meaning or verdict semantics.

13. Blocking conditions
Unresolved authority conflict; blocking non-compliance; insufficient fit evidence for a required authority-bearing Claim/action after reasonable acquisition; generated/source semantic drift; duplicate/conflicting Rule owners; unreconciled breaking compatibility impact.

14. Release relationship
SO-10 composes release readiness from Revision Identity, self-consistency, assurance required by impact class, consumer validation where required, migration/rollback where required, and blocking-finding closure. SO-09 does not assign release state.
