AIRepo — SO-09 Validation and Conformance  
Status: PUBLIC CANONICAL / AIRepo 1.0.0  
Public release identity: AIRepo 1.0.0

1. Mission  
Own reusable applicability, verification, validation-result and conformance-verdict semantics for AIRepo while keeping concrete validation evidence outside reusable framework semantics.

2. Minimal conformance model  
Normative Rule → applicability → verification intent → concrete evidence → result → verdict.

3. Applicability  
For each Rule: applicable | not applicable | unresolved. Not-applicable requires evidence that the activating condition/consumer is absent. Unresolved applicability cannot be silently treated as satisfied.

4. Validation results  
satisfied | approved deviation | non-compliant | insufficient evidence | conflict.

5. Evidence acquisition model  
When required evidence is missing, stale or ambiguous, the default next action is read-only investigation/acquisition when safely possible. Fail-closed applies before an authority-bearing outcome when evidence remains insufficient.

6. Self-consistency  
The framework candidate must validate: one semantic owner per fact; no duplicate active Rule IDs; all active Rules resolvable; generated/source consistency; closed replacement references; no competing authority; no project-specific semantic dependency; deterministic assurance classification.

For a published Machine Projection additionally validate: exact release/source binding; complete active Rule/SO identity coverage; no unknown owner references; no provider-specific semantic fields; deterministic normalized payload; stale detection on source-hash mismatch.

For a Localized Projection additionally validate: exact canonical source binding; locale identity; stable identifiers unchanged; stale detection; canonical-source precedence.

7. Independent assurance  
Class A: not required by default.  
Class B: only when targeted risk warrants it.  
Class C: required independent review.  
Class D: required independent adversarial review.

8. Consumer validation  
Consumer validation is targeted to affected contracts and failure modes. Class C/D changes require affected-consumer validation; unrelated consumers do not need ceremonial revalidation. Backward-compatible optional projections do not require a consumer to adopt the projection itself to demonstrate compatibility.

9. Concrete evidence records  
Validation-run evidence is non-authoritative evidence bound to an exact Framework Revision and exact consumer revision. Where evidence is produced after the governed subject, record both `subject_revision` and `evidence_revision`; the latter must not redefine the former.

10. Generated verification view  
A generated Conformance View or Machine Projection may combine Rule IDs, applicability semantics and verification intent for execution convenience. It is a deterministic projection and cannot own Rule meaning or verdict semantics.

11. Blocking conditions  
Unresolved authority conflict; blocking non-compliance; insufficient evidence for a required authority-bearing claim/action after reasonable acquisition; generated/source semantic drift; duplicate/conflicting Rule owners; unreconciled breaking compatibility impact.

12. Release relationship  
SO-10 composes release readiness from Revision Identity, self-consistency, assurance required by impact class, consumer validation where required, migration/rollback where required, and blocking-finding closure. SO-09 does not assign release state.
