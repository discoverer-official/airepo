AIRepo — SO-03 Semantic Model
Status: PUBLIC CANONICAL / AIRepo 1.1.0
Public release parent: AIRepo 1.0.0

1. Mission
Define the minimal semantic vocabulary used by AIRepo to reason about repository organization and conformance evidence without coupling the framework to a particular filesystem, platform, provider, language or repository host.

2. Core concepts
Asset — an engineering artifact or externally hosted engineering resource that a repository consumer must resolve.
Semantic Area — a responsibility grouping justified by current consumers and lifecycle, not a mandatory directory.
Authority Owner — the actor or accepted source entitled to decide a semantic fact/state class.
System of Record — the canonical persistence/source for a state class.
Consumer — human, AI agent, tool, build, service or project process that uses an asset/contract.
Locator — a physical or logical reference used to find an asset; never authority by itself.
Revision Identity — immutable/reconstructable identity satisfying SO-10.
Projection — generated/read-only representation derived from canonical semantics.
Machine Projection — deterministic structured Projection for machine discovery, identity, applicability and validation; never a semantic owner.
Localized Projection — translated human-readable Projection bound to exact canonical source identity; never a semantic owner.
Claim — a bounded proposition about an exact or otherwise unambiguously resolved subject whose truth is being assessed.
Evidence — observation or record used to support or challenge a Claim; not authority solely by existence.
Evidence Fitness — the claim-relative suitability of Evidence considering subject binding, verification-method observability, material-input coverage, freshness/staleness and declared comparability limitations.
Profile — project-owned declaration of AIRepo applicability/adoption choices.

3. Reference relations
OWNS — authority/semantic ownership.
CANONICAL_IN — System-of-Record relation.
CONSUMED_BY — active consumer relation.
DEPENDS_ON — semantic/compatibility dependency.
LOCATED_AT — non-authoritative locator.
GENERATED_FROM — projection/localization lineage.
EVIDENCE_FOR — evidence-to-claim relation.
REPLACES / SUPERSEDES — lifecycle replacement relation.

4. Classification dimensions
For a material asset determine: semantic responsibility; owner; canonical source/SoR; consumer; lifecycle/durability; confidentiality/access class; reuse scope; generated/manual status; compatibility boundary; placement/storage constraints where relevant.

For a material conformance Claim determine: subject identity; applicable Rule/profile; claimed property/boundary; verification intent; evidence method; Evidence Fitness; limitations; result.

5. Physical mapping
Semantic Areas may map to directories, files, packages, repositories or external services. AIRepo never requires a universal filesystem topology. Physical organization is acceptable when it preserves the semantic model, discoverability and project authority.

6. Conditional AI asset semantics
Prompt, dataset, evaluation, trace and generated-output classes are recognized only when present and relevant. AIRepo owns their repository-facing classification/ownership/provenance/lifecycle semantics, not the underlying domain methodology.

When a behavior or reproducibility Claim depends on context composition, capability exposure, workflow, policy, runtime, model or other externally owned semantics, AIRepo references the material identities/evidence supplied by those owners. AIRepo does not create a competing behavior/context/runtime object model.

7. Machine-readability contract
Canonical semantic authority remains the Release Manifest plus Markdown semantic owners. Stable IDs and structured fields may be emitted as a deterministic Machine Projection. A Machine Projection MUST bind exact framework/release identity and source hashes; MUST be generated-only; MUST fail validation when stale or incomplete; MUST NOT introduce semantic facts absent from canonical owners; and MUST NOT be required for a consumer that can consume canonical Markdown directly.

8. Localization contract
A Localized Projection MUST bind framework version, release identity, canonical source identity/hash, locale, translation status and validation status. Stable IDs, hashes, paths and schema keys remain invariant across locales. Canonical source wins automatically on disagreement. A stale localization is non-current derived content, not a competing authority.

9. Anti-patterns
- treating folder names as semantic authority;
- separate registries for a handful of assets without active consumers;
- duplicate canonical state across repository and external platform;
- generated artifacts without source/revision lineage;
- exact-revision validation treated as sufficient without testing whether the method can observe the claimed property;
- mocks or fixtures used to claim an unexercised end-to-end boundary;
- provider-specific object models promoted to universal semantics;
- conditional ecosystem concerns made mandatory for all repositories;
- hand-edited machine or localized projections treated as canonical truth.
