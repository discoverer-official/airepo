AIRepo — SO-10 Release and Governance  
Status: PUBLIC CANONICAL / AIRepo 1.0.0  
Public release identity: AIRepo 1.0.0

1. Mission  
Own change classification, compatibility governance, Revision Identity requirements, deprecation/removal rules, release-readiness composition and Human Approval boundaries.

2. Change classes  
Class A — Editorial / Derived: no semantic or compatibility change. Automated consistency only.  
Class B — Compatible Clarification: semantics clarified without consumer-contract change. Targeted validation and self-review.  
Class C — Material Semantic / Framework Behavior: requirements or consumer behavior materially change without necessarily breaking compatibility. Requires impact analysis, targeted consumer validation, independent review and Human Approval before canonical adoption.  
Class D — Authority / Breaking / Safety-Critical: authority boundaries, compatibility contract or safety-critical behavior changes. Requires RFC/ADR, alternatives, migration/rollback, adversarial review, affected-consumer validation and Human Approval.

3. Complexity proportionality  
Every change receives a lightweight complexity screen: active consumer/failure mode; new owner/SoR/location/validator/workflow; compatibility edge; migration/rollback; less irreversible alternative. A full Complexity Budget is required only for material structural/lifecycle impact.

4. Revision Identity contract  
Every releasable Framework Revision must be immutable or reproducibly reconstructable and provide stable revision identifier, exact source-set binding, mutation detection, recoverability and binding of generated views/evidence to the same revision.

5. Derived projection governance  
Machine and Localized Projections are optional derived release artifacts, never semantic owners. A release MAY publish them for convenience. Consumers MUST NOT be required to run a generator. Projection staleness or mismatch blocks claims about that projection but does not silently rewrite canonical semantics.

Pure localization correction with unchanged canonical semantics does not require a Framework SemVer change. A canonical semantic change invalidates affected localized projections through source binding.

6. Release readiness predicate  
A candidate may be presented for Human release decision only when exact Framework Revision is resolved; generated views match canonical semantic owners; self-consistency passes; assurance required by the highest applicable change class passes; required affected-consumer validation passes; migration/rollback exists when required; and blocking findings/conflicts are resolved or explicitly presented for Human Decision.

7. Compatibility  
Stable Rule IDs are not silently reused. Breaking removal or incompatible reinterpretation requires explicit compatibility treatment and Human Approval. Additive optional projections and additive Rule/guidance that preserve prior consumer validity are compatible MINOR changes.

8. Deprecation and migration  
Deprecated semantic identifiers remain discoverable with replacement and migration guidance for the declared support window. Historical evidence is retained as evidence, not rewritten as current semantics.

9. Human Approval boundaries  
Required for canonical semantic adoption of Class C/D changes, authority-model changes, breaking compatibility, individual Rule removal/incompatible reinterpretation, freeze/promotion and other explicit framework-owner decisions. Not required for ordinary research, evidence acquisition, generated-view regeneration, Class A changes or bounded implementation work already authorized by an accepted RFC.

10. No governance recursion  
Do not create a new registry, approval workflow, release service, lifecycle state machine, localization service or dedicated projection runtime when static derived artifacts and deterministic validation satisfy the requirement.

11. Frozen-parent rule  
AIRepo 1.0.0 is the first public stable release. Internal pre-public baselines remain immutable provenance and rollback evidence. Public Semantic Versioning starts at 1.0.0; future release changes follow this document’s compatibility and governance rules.
