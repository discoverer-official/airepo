AIRepo — SO-08 Migration and Compatibility  
Status: PUBLIC CANONICAL / AIRepo 1.0.0

1\. Mission  
Own reusable semantics for structural migration, compatibility preservation, replacement mapping, deprecated aliases and rollback.

2\. Compatibility principle  
Repository reorganization must preserve or explicitly migrate active consumer resolution, authority, canonical state, contracts, references, generated-view lineage and required evidence.

3\. Migration inputs  
Current Project Profile and revision; accepted target design; affected Rule IDs; affected consumers; old→new responsibility/locator mapping; compatibility impact; validation plan; rollback trigger and procedure.

4\. Replacement model  
Every retired semantic owner, document entrypoint or stable identifier with active consumers receives an explicit replacement. Historical evidence keeps historical references; it is not rewritten to pretend it used successor semantics.

5\. Alias model  
Deprecated aliases may preserve old document numbers/titles/locators during migration. Aliases are non-authoritative, resolve to the new semantic owner or generated view and must not become permanent duplicate truth.

6\. Migration classes  
Editorial/derived relocation with no semantic or consumer impact may be Class A.  
Compatible structural/navigation change is normally Class B.  
Material consumer-facing structural/semantic migration is Class C.  
Breaking authority/contract migration is Class D.  
SO-10 determines assurance required by the highest applicable class.

7\. Rollback  
Every material migration defines the bounded action needed to restore prior authority, identity and consumer resolution. Frozen v2.0.0 is the framework-level rollback parent for this successor evolution.

8\. Generated-view migration  
Generated indexes, catalogs, mappings and agent bundles are regenerated from successor canonical semantics. They are never hand-migrated as independent semantic copies.

9\. Consumer migration  
Playbook and AID remain independently pinned until their project authority adopts the successor. The framework does not mutate consumer repositories merely because a successor candidate exists.

10\. Breaking-rule boundary  
Removal or incompatible reinterpretation of an active Rule is not authorized through a structural mapping. It requires explicit compatibility treatment and Human Decision under SO-10.
